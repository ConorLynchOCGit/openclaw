# Cross-Domain Memory Families

## Purpose

This doc separates:

1. the six families that are already real and landed
2. the flattening phase that must happen before major expansion
3. the likely additional domain-neutral families still needed later

## Current implemented families

- response-style preference / requirement
- project facts
- recurring procedures
- workflow lessons
- project rules
- unmet needs

These are now at practical parity, but they are not fully identical in
capability envelope.

## Near-term roadmap rule

Do not use this doc to justify immediate new family work.

The near-term roadmap is:

1. flatten the family substrate
2. reduced-profile self-improving capture integration
3. learned-guidance advisory planning
4. only then resume cross-domain family expansion

## Why expansion waits

The remaining bottleneck is not missing family taxonomy. It is accidental
parallel implementation across the six landed families.

Adding more families before flattening would multiply:

- ingestion duplication
- lifecycle duplication
- retrieval scoring duplication
- application-policy duplication
- proofing duplication

## Design rule

When family expansion resumes, prefer a small number of domain-neutral families
over a long tail of domain-specific vertical families.

Examples:

- geology should not require a dedicated geology family
- marketing should not require a dedicated marketing family
- physical science should not require a dedicated science family

## Likely later domain-neutral families

Recommended later families:

1. decision + rationale
2. observation / result / finding
3. terminology / ontology / canonical definition
4. entity profile
5. risk / hazard / safety constraint
6. metric / baseline / threshold
7. hypothesis / open question
8. audience / stakeholder model
9. source trust / authority ranking
10. exception / edge-case rule

## Important caution

Do not read “practical parity” as “all future families can now be added
cheaply.” Practical parity solved user-facing inconsistency. Flattening is what
reduces future-family execution cost.
